# Architecture

Domus has two scopes, and one question decides which a piece of work belongs in.

## Common and site

- **Common** is the `domus` package in `src/domus`: the tools, objects and patterns that suit any user, any
  property and any location. It's what the container ships.
- **Site** is one property's project folder: its data (`data/`), settings (`data/site.toml`), wall options
  (`options/`) and sources (`sources/`), plus any tools and tests written only for it.

**What goes where.** Would someone with a different property, somewhere else, want it unchanged? Then it belongs in
common, with its numbers coming from settings or data. If it names one property, survey, document or product, or only
makes sense for one site, it belongs in that site. When you're not sure, start in the site.

**From a site to common.** A site tool that proves general moves into common once its numbers come from settings or
data, it has a test on the made-up sites, and it's documented. The changelog says what sites can then drop.

## Where sites live

- `site/` in a copy of this repo holds generic templates: a README, notes for agents, an example tool and example
  tests ([site/README.md](site/README.md)). Git ignores everything you add there, so one property's customisations
  stay out of the public repo.
- `sites/<name>/` holds more than one property, and git ignores it too. Any other folder or repository works as well:
  point Domus at a site with `--site PATH` or `DOMUS_SITE`.
- The files `domus new` and `domus create` write come from `src/domus/templates/`.
- The made-up demo site (`domus demo`) is the complete working example, generated by code. `tools/made_up_sites.py`
  adds a richer one, the demo moved abroad and one in an older format. CI builds them all with a pull request's base
  and its head, and holds the one abroad to the demo within 1.5 mm.

## Rules

1. **The build is a pure function of the site folder.** The same folder, with the same version of Domus, builds the
   same model on any machine.
2. **Places come in through importers that write an ordinary site folder** (`domus.importers`): New Zealand's
   (LINZ, with OpenStreetMap when there's no key), anywhere's (OpenStreetMap and the Copernicus ground model), and your
   own boundary and rasters (`domus new`). The site's grid, its heights' datum and its credit line are data in the
   site, not defaults in common. A site is on a grid in metres, each raster is read on its own grid, and the build
   works from the site's origin, so the same site on any grid builds the same model. The build never calls an
   importer.
3. **A site says its format.** `[domus] format` in `data/site.toml` lets later versions of Domus read older sites:
   each migrates an older site in memory, for good, and `domus site upgrade` writes the migration into its files.
4. **Nothing about one property is built into common:** no names, coordinates, documents or one house's looks.
5. **Real sites stay out of git.**

## The package

`src/domus` is laid out by what each part does:

| Part | What's in it |
|---|---|
| `geo/` | The site's grid and datums (`crs`), rasters read on their own grids, GeoJSON, meshes, fits |
| `model/` | The model's parts: the ground (`terrain` reads the site's, `tin` triangulates), the house and its looks, walls, small features, plants (`canopy` reads the site's, `vegetation` draws), drains |
| `options/` | The wall options: `scheme` works them out, `design` reads a site's for it, `sketch` turns a drawing into one |
| `build/` | The build, and its cache |
| `export/` | A built model for other software: glTF, and IFC through the optional IfcOpenShell |
| `checks/` | `domus prep check`'s rules, and the viewer's checklist and video walk (`enrich`) |
| `capture/` | Videos into placed clouds, and phone scans |
| `prep/` | A site's documents and photos into its data |
| `importers/` | Places into site folders: New Zealand's (`nz/`), anywhere's (`osm`) |
| `project/` | The site folder: the Site Domus reads, its settings' schema, formats and upgrades, trusted extensions, layer edits, `domus new` and the demo |
| top level | The command line, the server, the public API (`api`, `testing`), `create`, the viewer and the templates |

The modules that moved there in 2026.11.38 can still be imported by their old names (`domus.terrain`, `domus.video`,
...), which are the same modules, so a site's tools written before keep working.

## Settings and imports

Every setting a site can hold is declared once, with its default and a line of help, in `domus.project.schema`, and the
code reads settings through it. The tests fail on a setting the code reads that the schema doesn't declare, or reads
with another default, and docs/site-format.md's tables are written from it. Import rules in pyproject.toml, checked in CI, keep the server on
the standard library, the model's pure parts free of the site and the app, and the command line on top. The pure parts
are the house and its looks, the walls and their looks, the small features, the plants (`vegetation`), the ground's
triangulation (`tin`), the wall options' working out (`scheme`), the mesh helpers and the drains: the build, a workflow,
reads the site (`terrain`, `canopy`, `design`) and hands them what they draw from.

## The build

`domus build` writes the model from the site folder alone. It keeps what it can reuse in the site's
`.domus/build-cache/`: the ground's pictures and each wall option's layers, each with a key made of everything it's
built from (the Domus code, the site's files, and for an option its own file and what it takes from the others). A
part whose key hasn't changed is taken whole, so a cached build is byte for byte a fresh one; proofs use
`domus build --fresh` anyway.

## A site's own code

A site's tools and tests write data the build reads: layers, settings, rasters. A tool can also run in the build, as
an extension (`[domus] extensions`, [docs/api.md](docs/api.md)), drawing layers of the site's own, but only on a
machine that trusts it as it is (`domus site trust`). A build with an untrusted extension stops; the container image
trusts none, and the server never imports a site's code.

## The public API

Site tools, a site's own tests and agents use `domus.api` and `domus.testing` ([docs/api.md](docs/api.md)): open a site,
read its lot, house, layers, ground and options, evaluate an option, build, check and export. What they offer changes only
after a deprecation in an earlier release and a "For site projects" note in the changelog. The rest of the package is
internal, so common can change behind the API without breaking a site's tools. A process can hold several sites:
Domus's modules read the current site (`domus.project.site`), and each site keeps what Domus reads of it.

## Where it's heading

The agreed plan takes Domus there in phases, each proved by identical builds of made-up and real sites before the
next starts:

| Phase | What it brings |
|---|---|
| 0 | This layout: `site/`, these docs, made-up sites built and compared in CI, and small fixes such as UTF-8 reads and gzip |
| 1 | A public API for site tools and tests (`domus.api`, `domus.testing`), raising errors instead of exiting |
| 2 | A settings schema, site formats read and upgraded in memory, and import rules checked in CI |
| 3 | Any location: rasters read on their own grid, sites on a metre grid, and sources for New Zealand, anywhere (OpenStreetMap) and your own files |
| 4 | The model as pure functions, builds that redo only what changed, and site extensions that run only where they're trusted |
| 5 | General tools that grew in real sites, moved into common |
| 6 | The package tidied into subpackages |

Beside the phases: a newer three.js in the viewer, a house that can keep an IFC master changed through one edit
path, and shared geometry between the viewer and the build.
